# 多系統共用登入入口：設計與選型說明

本次成果是組織共用登入入口的十款前端原型。各款共用同一份組織替換欄位、示範系統、公告、服務狀態與互動程式；差異集中在資訊配置、導覽及視覺呈現。登入後僅示範系統清單、無權限說明與導向結果，沒有建置業務系統功能。

選型以三個問題為核心：**知道如何登入、知道服務是否受影響、知道遇到問題怎麼辦**。以下內容是根據原型結構與程式進行的設計評估，未經使用者測試，不代表已證實改善效率，也不是無障礙認證。

## 共同資訊架構與優先順序

| 層級 | 使用者要知道的事 | 共用實作與呈現原則 |
|---|---|---|
| 組織辨識 | 這是哪個組織的入口？ | `[Logo]`、`[組織名稱]`、「資訊服務共用入口」與工作帳號用途說明；入口品牌不借用單一系統名稱。 |
| 本次操作 | 我要前往哪裡？下一步是什麼？ | 表單前顯示直接入口或目標系統；送出按鈕及瀏覽器頁面標題同步反映目標。 |
| 主要任務 | 帳號怎麼填？如何登入？ | 工作帳號、密碼、可見標籤、必填提示、顯示／隱藏密碼與主要登入按鈕。 |
| 當前影響 | 現在可以繼續嗎？ | 預設「狀態未確認」；維護或異常影響本次目標時，在表單送出前呈現影響範圍、現在可做的事、替代方式與更新時間。 |
| 登入協助 | 忘記密碼、第一次使用或權限不足怎麼辦？ | 表單附近保留忘記密碼、帳號申請、權限申請與首次使用；錯誤說明附重試或求助途徑。 |
| 公開服務資訊 | 哪些消息與我相關？ | 公告先顯示最多兩則，依重要程度排序；可篩選組織／系統通知，查看全部及逐則詳情。部分設計將一般公告放在原生展開區。 |
| 支援服務 | 無法登入也找得到人嗎？ | 免登入問題回報摘要、資訊室聯絡方式、服務時段、非服務時段支援與三則常見問題。 |
| 使用與維護說明 | 這些資料如何使用、由誰維護？ | 維護單位、隱私與展示說明、共用工作站提醒、整合條件說明。 |

正常情境由登入主操作領先，一般公告不會主動彈出。狀態的正常、部分異常、維護中、未確認均有文字；顏色只是輔助。重大通知不依賴使用者先打開公告：直接入口遇到部分系統異常、或目標系統確實受影響時，表單前都有操作相關通知。其他系統的局部異常不會冒充整個組織入口失效。

## 主要操作流程

### 直接開啟共用入口

1. 確認組織與帳號說明，看到「登入後選擇系統」。
2. 檢視服務狀態；影響部分系統的通知說明哪些系統仍可用。
3. 按「填入示範資料」後送出。未填欄位顯示各自錯誤，焦點移至第一個缺漏欄位。
4. 示範處理期間停用登入按鈕，避免重複送出。
5. 成功後顯示固定示範權限的系統清單；目前示範可用權限為人事差勤與電子簽核。
6. 選擇系統後呈現導向結果。受影響的服務另顯示現況，可改選其他系統或取得支援；沒有開啟外部網站。

### 由特定系統導入

1. 展示控制或已知 `target` 代碼指定來源系統；登入前清楚寫出目標名稱。
2. 僅在本次目標受影響時，於表單前顯示對應的維護／異常通知。
3. 完成示範登入後，依固定示範權限與展示服務狀態，呈現導向結果、服務受影響結果，或「登入成功但沒有使用權限」。
4. 無權限結果提供權限申請與可用系統清單。登入與系統授權分別說明，避免誤認為應反覆重設密碼。
5. 無法識別的目標代碼回到共用入口，並告知登入後可選擇系統；不接受任意網址作為導向目的地。

### 失敗、逾時與求助

| 情境 | 原型行為 | 使用者下一步 |
|---|---|---|
| 尚有必填欄位 | 欄位旁顯示文字，標示無效狀態並移動焦點 | 填入示範資料後再次送出。 |
| 非示範帳密 | 清除輸入，說明本原型只接受示範資料 | 使用「填入示範資料」；沒有對真實帳號進行查詢。 |
| 帳號或密碼驗證失敗 | 用一般化訊息表示無法驗證，不指出帳號是否存在 | 確認輸入、重設密碼或使用免登入支援。 |
| 網路／登入服務無法使用 | 區分連線問題與帳密問題，提供示範錯誤代碼 | 確認網路後再試，或產生問題回報摘要。 |
| 工作階段逾時 | 提示重新登入並保留目標情境 | 重新填入示範資料；不默默丟失原先欲前往的系統。 |
| 成功但無權限 | 登入結果明確說明尚未進入系統 | 查看權限申請、改選可用系統或聯絡審核窗口。 |
| 需要協助 | 不依賴登入即可查看 FAQ、聯絡資料與回報摘要 | 將摘要交給正式窗口；本頁不自動送出報修或寄信。 |

各款頂部都有與產品畫面分隔的「前端原型」展示控制，可獨立切換直接／目標入口、服務狀態及登入結果。展示控制的「正常」和「成功」是模擬情境，不能當作服務監測或真正身分驗證的證據。

## 從資訊室服務角度主動補充的功能

| 補充內容 | 加入原因 | 前端原型的界線 |
|---|---|---|
| 目標系統同步出現在情境提示、登入按鈕與頁面標題 | 多個分頁、跨系統導入或稽核詢問時，能重新確認本次操作目標。 | 僅辨識公開示範系統，不表示已建立任何 SSO 信任關係。 |
| 狀態未確認與資料更新時間 | 沒有監測資料時，讓同仁理解「不知道」與「正常」不同，避免錯誤安心。 | 預設不連接監測平台；時間標為示範，尚未取得資料時明示。 |
| 重大影響依目標系統呈現 | 讓受影響者送出前就知道限制，同時保留其他系統的工作路徑。 | 替代作法未提供時明示未確認，不自行承諾恢復時間。 |
| 免登入支援及非服務時段欄位 | 無法登入的人最需要求助；醫院與大型組織還須考量夜班及共用工作站。 | 分機、信箱、服務時段及值班方式為替換欄位，須由正式單位核定。 |
| 可複製的問題回報摘要 | 減少反覆詢問目標系統、發生時間、錯誤代碼與現象。 | 不自動送出；不要求密碼、驗證碼或敏感業務內容。展示發生時間由本機產生，不等於伺服器稽核時間。 |
| 登入與權限分開說明 | 避免使用者在已驗證但無授權時誤以為帳密錯誤。 | 權限名單固定為示範資料；正式授權必須由後端執行。 |
| 共用電腦與登入紀錄說明 | 醫院共用設備應避免延續前一位使用者的身分，個人紀錄也不能在登入前暴露。 | 不提供保持登入或記住帳號；電腦名稱、作業系統與個人歷史登入紀錄列為整合條件，沒有填入看似真實的裝置資料。 |
| 公告範圍、優先序與效期 | 協助資訊室維持與當下任務有關的內容，避免過期或不適用公告持續干擾。 | 以固定示範日期評估公開公告；正式環境須由後端過濾可見範圍。 |

未加入天氣、時鐘、裝飾動畫、服務可用率或業務數據儀表。這些內容沒有直接協助完成登入、理解狀態或取得支援。

### 差異檢查方法

比較五項可觀察的面向：**結構、登入位置、公告呈現、導覽方式、視覺語言**。只更換主色、背景或圓角不另外算一項差異；相同配置的改名也不算。手機為了可用性收斂為登入優先的單欄，並不表示桌機結構差異消失，但仍須保留各款可辨識的閱讀或導覽方式。

02 與 09 都保留窄幅置中登入，不能把這項共同基礎說成差異。09 已改為直接可見的精簡公告索引；02 的公告需展開。其餘差異是 02 將完整支援收進展開區、09 將支援直接放在閱讀流程中，以及上方工具帶／底部常駐導覽。此組合按支援資訊結構、公告呈現與導覽方式計算三項差異，不靠配色或圓角湊數。

## 一致標準下的定性評估

以下為設計審查，沒有替使用者測試給出精確分數。「有利」是結構帶來的預期優點，「需留意」是正式試用應觀察的地方。所有款式使用共同的表單標籤、錯誤狀態、鍵盤焦點與支援流程，無障礙欄比較的是各版配置額外需要驗證的事項。

| 款式 | 登入辨識度 | 訊息理解度 | 求助便利性 | 無障礙 | 跨裝置體驗 | 維護成本 |
|---|---|---|---|---|---|---|
| 01 | 有利：左側獨立主表單 | 有利：狀態與公告分組 | 表單捷徑近，完整服務台在下方 | 結構直接；檢查窄欄標籤換行 | 雙欄轉單欄，順序容易理解 | 相對低，常見格線與共用卡片 |
| 02 | 有利：單一置中焦點 | 狀態直見；一般公告需展開 | 捷徑可達，完整支援折疊 | 需確認展開區的焦點及可發現性 | 窄幅自然縮放；桌機縱向較長 | 相對低，原生展開元件易維護 |

## 正式入口前三款建議

### 優先方案：01 晴白服務台

適合作為未限定裝置與職類時的預設方案。組織、登入、狀態、公告與支援區的關係直接，資訊室也較容易在不破壞主操作的情況下維護內容。使用者不必先理解特別的導覽模式。

正式採用前應補入組織品牌與已核定的免登入聯絡資料，設定公告摘要字數及數量上限，並確認一般桌機高度下的登入按鈕位置。若實際公告很長，詳細內容留在展開頁面，不把全部技術說明塞入右欄。

### 工作站方案：08 高效工作站

適合桌機與共用工作站比重高的醫院值班區、櫃台或行政辦公室。登入、服務消息與支援並置，特別適合一邊確認操作狀態、一邊尋找資訊室協助的情境。「高效」是設計名稱，不是已測量的效率結論。

正式採用前應用實際最常見螢幕尺寸確認三欄寬度，完整驗證 768px 左右的平板重排，核定值班及非服務時段支援方式。右欄只保留能直接促成求助的內容，避免擴充成沒有優先序的連結清單。

### 導入方案：05 清楚三步

適合剛建立共用入口、系統眾多，或常遇到同仁不清楚登入後會去哪裡的組織。三步提示把「確認組織與目標」「完成登入」「選擇或返回系統」說清楚，也有助於區分共用畫面、驗證及系統授權。

正式採用前應測試流程文字是否符合既有帳號習慣，確認直接入口與目標入口的描述都正確；若實際架構包含 MFA，再增加與真實驗證階段一致的條件式提示。三步圖示目前是流程說明，不是三個獨立驗證頁面。

若實際使用資料顯示手機占大多數，可將 09 納入前三款的替代候選，並以實機驗證獨立底部導覽、內容捲動與軟體鍵盤。若首要目標是低頻使用者專注完成登入，可將 02 納為候選，但須確認使用者能發現展開式完整支援。深色 03 適合做有明確需求的候選，不宜僅因醫院存在夜班就預設所有人偏好深色。

## 資料、假設與示範範圍

| 類型 | 本次內容 | 使用界線 |
|---|---|---|
| 使用者已確認 | 多系統共用入口、正體中文、十款可比較前端、登入後僅示範清單與導向 | 作為設計範圍，沒有推論特定醫院的實際技術架構。 |
| 待提供替換欄位 | 組織名稱、Logo、資訊室／維護單位、分機、信箱、服務時段、值班方式、帳號及權限窗口 | 方括號欄位不是可使用的聯絡資料，正式上線前必須替換。 |
| 明示示範 | `demo.user`、示範密碼、人事差勤／電子簽核／採購申請、固定權限、公告、各種服務情境 | 不能作為真實系統名稱、業務公告、服務承諾或授權證據。 |
| 固定示範時間 | 公告資料使用 2030 年的固定參考時間；畫面標為「示範日」 | 用來重現公告發布、效期與排序，不代表已排定維護。 |
| 本機展示時間 | 問題摘要與錯誤發生時間 | 僅為操作原型時產生的本機時間；正式問題時間應由使用者確認並與伺服器紀錄關聯。 |
| 尚無即時資料 | 預設服務狀態「未確認」、更新「尚未取得」 | 不將無資料等同正常，也不承諾恢復時間。 |

合理假設包括：入口面向組織內一般同仁，但登入前的資料仍視為公開資訊；工作帳號的具體格式由資訊室核定；前端可以提供共用外觀，真實驗證與權限查詢留待整合；常見直接入口與目標入口都應能完成操作；共用工作站不預設延續工作階段。

此原型只接受示範帳密，送出後清除密碼，不呼叫登入 API，不以 cookie、localStorage 或 sessionStorage 儲存帳密及展示狀態。不要輸入真實密碼。回報摘要僅在頁面內產生，可自行複製，不會寄送或建立工單。

前端使用共用元件、資料與互動程式；字型採系統可用字型，圖示使用內嵌向量，核心登入不需要外部圖片。Bootstrap 與 jQuery 正式部署時應沿用本地資源，並納入版本、授權、更新與完整性管理；十款不應各自長期維護一份不同的登入規則。

## 影響正式整合的待確認事項

| 項目 | 需要確認的問題 | 決策影響 |
|---|---|---|
| 組織與入口品牌 | 正式名稱、Logo、共用入口稱呼、是否有正式／測試環境識別需求？ | 避免跨院區、跨環境或多分頁誤認。 |
| 帳號來源與帳號生命週期 | 使用人事系統帳號、AD／LDAP、既有身分平台或獨立帳號？新進、離職、調職與停用由誰維護？ | 影響帳號提示、申請／重設與同步作業。 |
| 驗證方式 | 是否有可用的登入 API 或身分提供者？帳密政策、驗證限制、帳號受限、密碼到期如何回應？ | 決定表單及錯誤情境；未驗證前避免揭露帳號存在與否。 |
| SSO、AD／LDAP 與 MFA | 是否真的導入 SSO？使用何種協定與信任範圍？AD／LDAP 是否作為帳號來源或驗證服務？MFA 何時觸發、如何備援？ | 不能由共用登入畫面推論已具備；須依確認架構建立條件式流程。 |
| 系統註冊與安全導向 | 哪些系統可公開？系統 ID、正式路徑、來源驗證與返回位置允許清單如何管理？是否保留安全的業務深連結？ | 防止任意外部導向，避免丟失目標或將未授權目的地交給前端自行判斷。 |
| 權限資料 | 由哪個服務回傳可用系統、角色及無權限原因？申請與審核窗口是誰？ | 驗證成功後才回傳個人化清單；前端隱藏不能替代服務端授權。 |
| 公告發布與治理 | 由誰編輯、覆核、發布及撤回？如何設定重要程度、適用系統、發布時間、有效期限、可見範圍與版本？ | 避免過期公告持續出現或敏感內容在登入前送達；公開與內部公告須在後端分流。 |
| 服務狀態來源與新鮮度 | 採人工核定、監測平台或事件管理系統？更新多久視為過期？資料源不可用時如何回到未確認？ | 避免以舊的正常狀態誤導操作；需定義最後更新、下一次更新的責任人。 |
| 異常與維護替代方式 | 業務單位是否已核定急件流程、紙本作業或其他替代管道？何時能對外說明？ | 只呈現已確認作法；沒有依據就不承諾恢復時間或處理時限。 |
| 支援與值班 | 免登入分機／信箱、服務時段、值班及非服務時段聯絡方式是什麼？需不需要院區或職類分流？ | 使用者在不能登入時仍有實際可用管道；原型的占位欄位需替換。 |
| 問題回報整合 | 對接何種工單服務？可公開使用的回報入口、必要欄位、錯誤代碼關聯與資料保留政策？ | 在提供足夠診斷資訊與避免密碼、驗證碼、病人或業務敏感資料之間取得平衡。 |
| 工作階段與共用設備 | 閒置逾時、最大時長、登出範圍、共用／個人設備政策、記住帳號與保持登入是否分開提供？ | 影響安全與使用中斷；不能預設共用工作站永久登入。 |
| 裝置與登入紀錄隱私 | 電腦名稱由哪個受管理服務提供？是否需要作業系統版本？最後登入時間、地點、電腦如何取得、保存、向本人呈現？ | 瀏覽器前端不能可靠取得完整電腦名稱；個人紀錄應驗證後取得，地點精確度與用途應明示。 |
| 內網與正式前端環境 | 院內瀏覽器、解析度、代理與網路限制為何？本地 Bootstrap／jQuery、字型、圖示如何部署與更新？ | 保證核心畫面可在內網開啟，避免必須連到外部 CDN。 |
| 無障礙與使用驗證 | 要支援哪些鍵盤、螢幕閱讀器、放大倍率、觸控設備與職類？ | 以實際裝置及同仁完成三個核心任務的觀察，決定正式選型及調整。 |

正式驗證建議讓行政、醫護／值班、主管與不熟悉資訊操作的同仁，分別完成「直接登入選擇系統」「辨識受影響目標並找替代行動」「登入失敗並取得免登入協助」三個任務。記錄是否能理解目標與狀態、是否找得到求助，以及卡住的地方，再決定最終版型；本文件不預先宣稱成效。
